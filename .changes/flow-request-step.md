### Added

- **`@reticlehq/core`, `@reticlehq/server` — a flow step can send a request to the app and judge the answer.** A step with `tool: "reticle_request"`, `request: { method, url, body?, contentType?, anonymous? }` and `response: { status?, contains?, absent? }` sends one request and checks the status and the body. Some rules live only on the server: a bad value is refused with 400, an undo after its time is refused, a signed-out caller is refused. A page that behaves can hide a server that does not, and before this step a flow could only drive the page. The request goes only to the app's own origin. It carries the page's cookies, so it runs as the signed-in user, unless `anonymous` is true. A redirect is not followed: the redirect is the answer that is judged. A request that changes data (any method other than `GET`, `HEAD` or `OPTIONS`) is sent only when the run confirms dangerous steps (`--confirm-dangerous`, or `confirmDangerous: true`), the same guard as a destructive click; a flow file cannot confirm it. A step with a declared `response` counts as a checked outcome. When the page's cookies cannot be read (the tab is not in a browser that Reticle drives), the step fails and says why, and it sends nothing. A request can also go as another account: `as: "<name>"` sends the `Cookie` header supplied for that name at replay (`RETICLE_SECRET_<NAME>`, or the call's `secrets`), never kept in the flow. A rule about who may change what can only be checked as someone else. When that session is not supplied, the flow is unverifiable and nothing runs.
