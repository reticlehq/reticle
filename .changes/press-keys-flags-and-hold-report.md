### Fixed

- **`@reticlehq/browser` — a modifier named in `press { keys: [...] }` now sets its own event flag, and a flag clears only when the LAST spelling of it is released.** `modifiers` is a fixed set of flags for one event, which is exactly why `keys` exists: a SEQUENCE whose held state changes partway through. The multi-key dispatcher read its flags from `args.modifiers` alone, so `{ keys: ['Control', 'k'] }` pressed Control and then dispatched the `k` keydown with `ctrlKey: false` — a shortcut handler checking `event.ctrlKey` did nothing while the action reported `dispatched: true`. The flag timing is the browser's own, read off a real Chromium rather than assumed: a modifier's own keydown carries its flag already true, its own keyup already false, and every event between carries the held state. Aliases make the RELEASE side its own case: `Control` and `Ctrl` are one flag, so `{ keys: ['Control', 'k', 'Ctrl'] }` presses it twice and releases in reverse — clearing it at `Ctrl`'s keyup turned it off while `Control` was still down, and every event after that reported `ctrlKey: false`. Each flag now counts its presses and clears at zero, which is what a real keyboard's own state machine does. A flag named in BOTH spellings at once is the same rule: `modifiers` holds its flags for the WHOLE press and never releases them, so its flags seed that count — without it, `{ modifiers: ['Shift'], keys: ['Shift', 'Tab'] }` cleared Shift at its own keyup, contradicting the argument that had just declared it held for the gesture. The dispatcher also reads `keys` through the same `pressKeysFromArgs` the routing half uses, so the two cannot disagree about which entries are keys. Closes [#1294](https://github.com/reticlehq/reticle/issues/1294).

- **`@reticlehq/server` — a real held press can no longer leave a key down, and refuses to replay when it cannot prove one is up.** A held chord is pressed key by key — modifiers down, the key last — and that sequence can fail PARTWAY: `Control` goes down, the key after it rejects, and the driver's copy of `Control` is still held. Those `down` calls ran before the `try` that released anything, so that path fell straight to the caller's synthetic replay, which presses the same chord again on a keyboard that is already holding a modifier. The same hole existed when the wait failed and the best-effort release failed too: the release failure was swallowed and the original error reached the caller as an ordinary drive error. The keys that actually went down are now tracked, every exit path cleans up, and a cleanup that cannot prove the keys are up throws `RELEASE_FAILED` — the one failure the caller refuses to answer with a synthetic replay. A cleanup that DOES succeed still hands back the original error, because the keyboard is clean and replaying is safe. Closes [#1295](https://github.com/reticlehq/reticle/issues/1295).

- **`@reticlehq/server` — `effect.heldMs` now reports the hold achieved on a real-keyboard press too.** `reticle_act` promises `effect.heldMs` says what was achieved, and on the real path the act result IS the effect block — but the driver's measurement was dropped on the way out, so an agent confirming a hold-to-confirm control armed read `undefined` on exactly the path `holdMs` had just been added to. The number is now measured (not echoed back) and forwarded, and is absent rather than `0` when the press held nothing. Closes [#1296](https://github.com/reticlehq/reticle/issues/1296).
