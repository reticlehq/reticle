### Fixed

- **`@reticlehq/engine`, `@reticlehq/server` — "the UI moved forward while a request failed" fired on apps that handled the failure.** On a page with no SDK signals, a correct optimistic control (disabled while the request was in flight, enabled again after a 500) got the same finding as a control that went on as if the request succeeded. A live feed that adds rows on its own made it worse. The rule now reads what became of the control that was acted on. A control rolled back to its earlier state, or still in its in-flight state, is not a finding. Changes to other elements decide nothing. When no acted control can decide and the app publishes no signal and no store change, the finding is the new absence-derived kind `ui-advanced-unsignalled`, which makes a verdict `unknown`, not `no`.
