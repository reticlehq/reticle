### Fixed

- **`reticle_memory` could return ANOTHER project's statements.** The read went out with the API key and `?subject` and nothing else, and a key covers a whole workspace rather than one repo — so with two repos linked to one workspace, the agent in repo B could be handed repo A's established knowledge, every entry valid and attributed to B. `.reticle/cloud.json` has always carried the project id; it just never reached the URL. The read now names the linked project, and the response is checked before any of it is read.

  The check is on the response **envelope**, not on the entries, and that distinction is the whole fix. `GET /v1/memory` answers `{ projectId, entries }` — the entries carry no project of their own — so an entry-level filter matched nothing, kept everything, and read as a fix while being none. A response whose envelope names another project, or names none at all, is reported as **unverified**: the tool answers `reason: "unverified"` with advice saying explicitly that this is not an empty corpus, `reticle memory` prints nothing and exits non-zero, and flow replay attaches nothing rather than carrying a sibling repo's knowledge into a verdict. All three readers share one helper, so a fourth cannot get a different answer. The entry-level filter stays as a second pass for a server that labels entries instead. The unlinked case (CI, and any install that never ran `reticle link`) named no project to begin with and reads exactly as it always did. Closes [#1247](https://github.com/reticlehq/reticle/issues/1247).

- **A git worktree's flows and intents were written into the main checkout.** Run the daemon in repo A, then connect an app from a worktree B that declares its own `projectId`: config discovery walks out from A's working directory and never crosses into a sibling checkout, so no directory could be matched, and the unmatched case fell back to the daemon's root unconditionally — B's intents, flows and runs landed in A's `.reticle/`, with the returned path naming A, so nothing looked wrong. The daemon now has to PROVE the named project is its own: it must declare the same id in its own `.reticle.json`, held to the same safe-path-segment guard as the id off the wire. A named project it cannot prove declines and goes to `~/.reticle/unmatched/<projectId>` instead — the refusal this asked for, and never into a tree nobody drove. A session that named no project at all (a pre-2.0 SDK) still resolves to the daemon's own root, which is the case that fallback was written for. Closes [#1244](https://github.com/reticlehq/reticle/issues/1244).
