### Fixed

- **`@reticlehq/engine` — a failed read of the app's own API did not change a passing verdict.** A replayed flow returned `ok` and `pass` while the same window held a `GET` that returned 500 and one that returned 502. The route and label checks held over stale content, and no finding named the requests. A new `read-server-fault` finding now names each request as "METHOD url → status", and the verdict is `unknown`, not `yes`. It applies to `act_and_wait`, `reticle_assert` and flow replay. The rule ignores a 4xx, third-party and dev-tooling traffic, a request before the action, a request that a later retry recovered, a failure that the app shows to the user and a failure that the step declared. On `act_and_wait` and `reticle_assert` it also ignores a read that failed the same way before the action, such as a background poll.
