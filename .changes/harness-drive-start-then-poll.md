### Changed

- **`@reticlehq/server`: a Harness drive no longer has to finish inside one tool call.** `reticle_verify { action: "explore" }` held the call open for the whole drive, so an MCP client's 60-second timeout cut nearly every drive off: the agent got no run id, the daemon kept driving and spending Harness credits, and a retry paid for a second drive. The call now starts the drive, waits up to `wait` seconds (default 45, at most 240) and answers either the full result or `{ status: "running", runId, steps, lastLine }`. Call it again with `runId` to wait for the end; add `stop: true` to stop the drive or `say` to tell its driver something before its next turn. A second explore on the same app while a drive runs returns that drive instead of starting another. A client that sends a progress token hears every step. The drive's answer is kept in `.reticle/runs/<runId>.drive.json`, so a new session or a restarted daemon can still read it. When the connection drops under a drive, the error now says the drive may still be running instead of telling the agent to retry. Drives started from the HUD or the platform's chat are announced once on the agent's next tool result, under `harness`.
