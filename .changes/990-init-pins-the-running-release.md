### Fixed

- **`reticle init` now installs the SDK at the version of the Reticle that is running it.** The scaffolder pinned the dependency install to the version on `@reticlehq/init`'s own manifest, which answers "which scaffolder is this" and not "which daemon is running". Those are the same number in a release we publish and an assumption about the tree a user's package manager assembles — and when the assumption was false, a daemon reporting one version scaffolded the app with an SDK from another, on a clean install, with every step green and nothing naming the disagreement. The page then never dialled the bridge and the agent was handed the version-skew remediation for a skew `init` had just created. The pin is now read from the running daemon (`InitHost.releaseVersion()`), and a host that cannot name a release falls back to the scaffolder's own version rather than dropping the pin and letting the registry choose. Refs [#990](https://github.com/reticlehq/reticle/issues/990).

  Not covered by this change: the CDN snippets for pages with no build step (plain HTML, Streamlit, Django) still pin `@reticlehq/browser` at the scaffolder's version, and skew remediation still names the package it expects rather than the one it found in the page.
