### Fixed

- **`@reticlehq/engine` — a `ref` on an `element` predicate is answered with `query`, not with advice to move it beside `until`.** `misplacedCallFields` reported every `ref` as a CALL argument one level too deep. That is right for the flat kinds, and misdirection for `element`, whose locator nests under `query`: moving a `ref` up on `act_and_wait` retargets the action, and `reticle_assert` has no `until` at all — so the advice cost the caller its target and the predicate still did not parse. An `element` predicate carrying a `ref` now says element predicates take `query`, not `ref`, beside the example the rejection already carried (#445). The move-beside-`until` clause stays for the kinds where it is right. Fixes [#1374](https://github.com/reticlehq/reticle/issues/1374).
- **The same answer now reaches the two spellings it was missing.** `type` is core's alias for `kind`, and reading `kind` alone meant `{ type: 'element', ref }` came back as `kind "unknown"` carrying the very move-beside-`until` advice the canonical spelling no longer gets; an `element` predicate wrapped in `anyOf`/`allOf` got no clause at all. Both are read now — the kind through one reader shared by the sentence and the clause, and the clause one level into `predicates`/`predicate`.
- **A `ref` written next to an existing `query` is answered with "delete it".** "Put the locator inside `query`" sends the caller to rewrite a field that is already right; when `query` is present the only action left is removing the extra `ref`. The accepted-field list in that sentence is derived from the schema rather than written out, so it cannot drift from `ElementQuerySchema`, and it no longer implies a raw element ref is never valid — it belongs in `query.scope`.
