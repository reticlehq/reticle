### Fixed

- **`@reticlehq/init` — Astro 7.2+ gets the pairing token through frontmatter, not `vite.define`.** On current Astro, `vite.define` does not reach the client pipeline: the served page script still contains the literal `__RETICLE_TOKEN__`, so `connect()` omitted `token` and the bridge refused with "no pairing token on the page". `init` now reads the file in frontmatter, puts it on a `<meta name="reticle-pairing-token">`, and connects from a local module with a static SDK import. Reading per request also means a token written after the dev server started is picked up on the next load instead of needing a restart. The example uses the same wiring and moves off the 7.0.3 pin. [#1008](https://github.com/reticlehq/reticle/issues/1008).
- **Framework e2e no longer leaks the test runner's env into the dev servers it spawns.** Vitest mirrors its own `import.meta.env` into `process.env`, and astro's dev plugin returns early out of `configureServer` when `process.env.VITEST` is set — so `astro dev` bound its port and logged "ready" with no page middleware attached, and every request fell through to `Cannot GET /`. The harness now strips the runner-only variables, keeps each dev server's output in `/tmp/e2e-<pkg>.log` (which CI already uploads), and waits for the app to actually serve its document instead of treating any reply on the port as ready.
