### Fixed

- **`@reticlehq/server` — after one flow left the app, `reticle verify` lost the verdicts of the flows after it, and blamed the port.** A flow that went to a page without the Reticle SDK (for example a server's 404 page) ended the browser session. The next flows then ran with no session. Each one got the generic "check your port" reason, although the setup had worked a moment before. Now the run checks the session of the page that it drives between flows. A loaded page on another origin, with no SDK, is reported lost at once. Any other page gets the wait that a replay gives its start page. So a healthy page whose SDK loads late is not reported, also an error page of the app. This also works when the last step of the flow goes to the dead page. A run that never had a session keeps the daemon's own diagnosis. The flow that left the app is reported as not proved. Its reason starts with `no session after navigation` and names the URL. The reason that the replay gave follows it. The run then opens the start URL again, so the next flows get their own verdicts. The next flow tries once, and its replay waits for its start page. If that flow also gets no session, each later flow is skipped while the page has no session. The reason names the flow and the URL where the session was lost. A later flow runs again as soon as the session is back.
- **`@reticlehq/server` — with your own tab of the app open, `reticle verify` could run its flows in your tab.** With no `--session-id`, each replay chose a tab, and the check after a flow counted any connected tab. When the driven page went to a page with no SDK, the run did not see the loss. The later flows clicked in your tab and passed, and the driven page stayed on the dead page. Now the run pins the tab of the page that it drives, and gives that id to every replay. The id is the session id that the page's SDK keeps for the tab. An SDK older than 2.5.0 does not keep it, and then each replay chooses a tab as before. `--session-id` still chooses the tab. Closes [#2060](https://github.com/reticlehq/reticle/issues/2060).
- **`@reticlehq/server` — the HTTP `/verify` endpoint (`reticle serve --http`) gets the same checks.** It uses the same runner. Each request starts with no pinned tab. With `--drive <url>`, the endpoint pins the driven page and opens it again after a lost session. With no driven page, it pins the only connected tab of the project and opens no page again. It names a URL only when the tab said where it was going. The MCP suite path (`reticle_flow_verify`) does not use this runner and does not change.
