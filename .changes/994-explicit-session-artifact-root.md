### Fixed

- **`@reticlehq/server` — a `sessionId` that names no session no longer routes artifacts into the daemon's own checkout.** Every tool that reads or writes a `.reticle` artifact resolves its directory from the connected session, and when the agent passed a `sessionId` that had gone (a tab that reconnected under a new id, a stale id held across a restart) the lookup failure was swallowed: the call fell back to `deps.reticleRoot`, which is wherever the daemon was started, and that is usually a different project. `reticle_intent { declare }` then wrote `intent.json` into a repository nobody had driven — a git-checked file, so the first sign of it was a `git diff` — and `reticle_intent { list }` answered with that other project's ledger, which from the outside is indistinguishable from this project having declared those intents. The same resolution backs runs, flows, capsules, baselines and the capability contract. A named session that resolves to nothing is now refused, with the connected sessions listed in the refusal so the call can be retried against a live one or with `sessionId` omitted; nothing is read and nothing is written. Calls that name no session are unchanged and still fall back to the daemon root, which is what makes declaring an intent before an app is running keep working, and a failed-assert capsule that cannot name a directory is skipped rather than filed in the wrong one — capturing evidence must not fail the verdict that found the bug. Refs [#994](https://github.com/reticlehq/reticle/issues/994).
