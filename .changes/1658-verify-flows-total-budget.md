### Fixed

- **`@reticlehq/server` — `reticle_verify` with `action: "flows"` or `"change"` had no total time limit and kept going after the session was lost.** The sequential replay waited on every remaining flow for a page that never came, and the MCP client gave up (about 300 seconds) with no result, even for the flows that had already run. The call now takes `budgetMs` (default 240000). When the budget is spent, or the session is gone after a flow, it stops and returns `status: "partial"` with the results so far, the flows in `notRun`, and `stopped` (the reason, the flow that lost the session, and one next action). The parallel run is unchanged. The default now applies to every caller of the sequential loop that does not pass `budgetMs`: before, a suite that took 250 s returned `pass`, and now it returns `partial` with the rest in `notRun`. `reticle verify` (the CLI) is the one non-MCP caller, and it passes its own 30-minute timeout as `budgetMs`, so CI runs keep running to the end; it still stops at a lost session and exits non-zero on `partial`. `SuiteVerdict.status` gains `partial` in `@reticlehq/core`, with the status and the stop reasons as named constants (`SuiteVerdictStatus`, `SuiteStopReason`). Closes [#1658](https://github.com/reticlehq/reticle/issues/1658).
