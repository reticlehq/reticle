### Fixed

- **`@reticlehq/server` — a malformed `reticle_intent` argument no longer deletes the intents already in `.reticle/intent.json`.** `reticle_run { tool, args }` checks that a tool's argument NAMES are known, never that their shapes are, so `intents: [{ id, statement, surface: "/authorize" }]` — `surface` as a bare string where the ledger requires `{ route: "/authorize" }` — reached the store unread and was written. Both readers then fail soft to empty by design, because a git-checked file a human can hand-merge really does arrive with a conflict marker in it; so one bad field made the whole ledger unreadable, every later `list` answered "no intents", and the next declaration wrote that emptiness back over everything the project had. The same shape took a `.reticle/intent/<subject>.json` shard down through `record`, whose missing arguments were coerced into an empty `id` and an empty `statement` and whose `status` was cast into the enum without being checked against it. Declarations and records are now parsed against the schemas their files are read back with, in the store, before the file lock — so every door reaches one check — and a batch is refused whole rather than half-written. The refusal names the field and says that nothing was written. Nothing valid changed: the nested `surface`, the `why`/`source`/`status` metadata and the merge-don't-replace semantics of `record` are as they were. Refs [#994](https://github.com/reticlehq/reticle/issues/994).
