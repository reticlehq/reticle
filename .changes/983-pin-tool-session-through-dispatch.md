### Fixed

- **`@reticlehq/server` — an action could run in one tab while the response described another.** A call that named no `sessionId` resolved a session twice: once in `runTool`, which is what the pool-lease heartbeat, the health envelope, ref provenance, the project ledger and the verdict's own attribution are hung on — and again inside the handler, which was handed the caller's arguments untouched. A tab that connected between the two resolutions (a parallel agent, a reopened preview) wins auto-selection on its fresher heartbeat, so the act landed in the newcomer while the answer described the tab the agent had been looking at. Nothing in that response looks wrong, which is what made it a false verdict in either direction: the predicate is graded against a page that was never driven. The wrong-tab ref guard could not see it either — it is asked whether a ref belongs to the tab _resolution_ picked, and its permission is only sound when that is also the tab the handler drives.

  The handler is now dispatched with the session the call already resolved, as a copy: the caller's argument object is never written to. An explicit `sessionId` — including one lifted off an `act_sequence` step — is still passed through exactly as written, so whether a stale id refuses or rebinds remains the resolver's decision, and a disk-only tool (`reticle_project`, `reticle_flow`, `reticle_intent`, …), which resolves no session, is still unscoped.

  This is one of the four failures reported under that issue. The other three — an expired lease rerouting to another connected tab instead of refusing, `reticle_session { action: "end" }` ignoring an explicit id, and `reticle_lease { action: "acquire" }` keying pooled contexts by origin rather than by caller — are untouched here. Refs [#983](https://github.com/reticlehq/reticle/issues/983).
