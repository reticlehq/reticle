### Added

- **`@reticlehq/browser`, `@reticlehq/server` — `confirmDangerous: true` on an action now answers that action's own `confirm()` with yes.** Before, Reticle answered every `confirm()` that a driven click opened with no, so that the tab could not wedge. There was no way to say yes, so a destructive flow behind a confirm could not be driven through its button, and agents called the API directly. Now the flag is the caller's yes to one `confirm()` of that one dispatch. A second `confirm()` in the same dispatch, a `prompt()`, a dialog that the next action opens, and a dialog that a person opens are not changed. When two actions are in flight at the same time, the `confirm()` is still declined. Only a flag that the caller passes to `reticle_act`, `reticle_act_and_wait` or `reticle_act_sequence` gives the yes. Every other path that sets the flag presses the control and still answers the `confirm()` no: a `reticle_act_and_wait` whose named target reads as destructive, a crawl, flow replay and verify, `compare` and a Harness run. The server sends the yes to the page as its own positive argument, so a page script that meets an older daemon answers no. In the page, only a `confirm()` that the action's handler opens synchronously is answered yes: one opened after an `await` or a timer keeps the old behaviour. On a leased tab, a real key press with the flag answers the native `confirm()` it opens. Reticle cannot see which code opened a dialog there, so the one `confirm()` that opens while the press is in flight is answered yes, also when a page timer opened it. A `confirm()` answered yes is recorded as `dialog.opened` with `answered: true`, on a leased tab too, and is not a declined dialog: a failed `until` after it stays `no`, not `unknown` / `dialog_declined`. Closes [#2167](https://github.com/reticlehq/reticle/issues/2167).
