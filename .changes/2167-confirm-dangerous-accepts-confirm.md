### Added

- **`@reticlehq/browser`, `@reticlehq/server` — `confirmDangerous: true` on an action now answers that action's own `confirm()` with yes.** Before, Reticle answered every `confirm()` that a driven click opened with no, so that the tab could not wedge. There was no way to say yes, so a destructive flow behind a confirm could not be driven through its button, and agents called the API directly. Now the flag is the caller's yes to one `confirm()` of that one dispatch. A second `confirm()` in the same dispatch, a `prompt()`, a dialog that the next action opens, and a dialog that a person opens are not changed. When two actions are in flight at the same time, the `confirm()` is still declined. Only a flag that the caller passes gives the yes: when `reticle_act_and_wait` sets it because the named target reads as destructive, the press goes through and the `confirm()` is still answered no. In the page, only a `confirm()` that the action's handler opens synchronously is answered yes: one opened after an `await` or a timer keeps the old behaviour. On a leased tab, a real key press with the flag answers the native `confirm()` it opens. Reticle cannot see which code opened a dialog there, so the one `confirm()` that opens while the press is in flight is answered yes, also when a page timer opened it. Closes [#2167](https://github.com/reticlehq/reticle/issues/2167).
