### Fixed

- **`@reticlehq/server` — `reticle verify --expect` dropped the predicate and answered about saved flows instead.** The predicate was only read when a Reticle daemon already owned the bridge port. On any other port state the flag was discarded without a word and the command carried on into the saved-flows path, where it reported — accurately, and about something else entirely — that there were no saved flows to verify. The output was byte-identical to the same command with no `--expect` on it, so there was nothing in it to debug. That is the documented route to a verdict for a client that never loaded the `reticle_*` tools, which means it failed for the people who had no other route. `--expect` now refuses when there is no daemon to ask, names the flag, says the predicate did not run, and gives the command that gets you a daemon on that port.
- **`@reticlehq/server` — `reticle verify --expect --storage-state <file>` graded the predicate against the wrong user.** The one-shot verdict takes its answer from the tab the running daemon already owns, and there is nowhere in that path to load a storage state — so the file was accepted and then ignored. A restricted-user absence assertion was evaluated against a logged-in admin tab and passed for the wrong reason. The pair is now refused by the parser, before anything binds a port or opens a browser, with a sentence saying what each flag does on its own. `--session-id` was already honoured on both paths and is unchanged. Refs [#993](https://github.com/reticlehq/reticle/issues/993).
