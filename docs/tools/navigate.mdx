`reticle_navigate` moves the connected browser tab to a URL, or reloads it in place with `{ "reload": true }`. Reach for it for a genuine document load: a deep link, a hard refresh, or the first visit. Clicking a link inside a single-page app is a route change, not a navigation, and does not need this tool.

```json
{ "url": "/deployments" }
```

Real response, with the throttled-tab `session` and `warning` fields trimmed off:

```json
{
  "ok": true,
  "url": "http://localhost:4310/deployments",
  "confirmed": false,
  "waitedMs": 5000,
  "note": "ok means the navigation was DISPATCHED, not that the page arrived. The SDK is torn down by the navigation itself, so nothing here can see the new document, and no session reconnected at the new URL within 5000ms. A slow app may still be on its way (an SPA reattaching under HMR can take 30-60s): navigate again with a larger timeout_ms, or call reticle_sessions to confirm a session reconnected before acting; if none appears, the page did not load or is not instrumented."
}
```

## `confirmed: true` when the page comes back in time

The daemon waits up to `timeout_ms` (default 5000) for the SDK to re-announce itself. When it does, you are told so, with the `sessionId` it came back as, and can act immediately without a `reticle_session { action: "list" }` round trip. This is a real reload response:

```json
{
  "ok": true,
  "confirmed": true,
  "note": "the page came back and re-announced itself under the same session id, so this session is live again. Anything captured before the reload is gone with the old document."
}
```

Read the second sentence, which is the one that costs people a turn. `confirmed: true` restores the session, not the evidence: every event, network call and console line captured before the reload went with the old document.

## `confirmed: false` is the honest part

A full navigation destroys the document the SDK was living in. Reticle cannot report on the new page from inside the old one, because the old one no longer exists. So it tells you what it actually knows: the navigation was dispatched.

Most tools would return `ok: true` and let you assume arrival. When the page then fails to load, or loads without instrumentation, you get a confusing cascade of "element not found" errors several calls later, with nothing pointing at the real cause.

`confirmed: false` with a `landedOn` URL is a different case: the page arrived, but the app sent it somewhere else, such as a login or route-guard redirect. `landedOn` says where the browser actually is.

`waitedMs` is how long Reticle waited for the page to come back before it stopped. The page may still arrive after that. A single-page app that reattaches under HMR can take 30–60 s, so give a slow app a larger `timeout_ms`:

```json
{ "url": "/deployments", "timeout_ms": 45000 }
```

## The pattern after navigating

```json
{ "url": "/deployments" }
```

then confirm a session reconnected:

```json
{ "action": "list" }
```

with [`reticle_session`](/tools/sessions), and only then look at the page. If no session appears at the new URL, the page did not load or is not instrumented. And you know that immediately rather than three calls later.

<Warning>
  **Refs do not survive a navigation.** A new document means new refs. Across one afternoon on the
  same fixture, the same "Sign in" button was `e105`, then `e305`, then `e3`. Re-snapshot; never
  carry refs across. Reticle refuses a stale ref rather than clicking whatever now occupies the
  slot, so the failure is loud, but it still costs you a turn.
</Warning>

## Back and Forward

To press the browser Back or Forward button, give `history` instead of a `url`. A synthetic Alt+ArrowLeft does not move a tab, and a URL navigation adds a new entry instead of moving through the entries the tab has. So use this to check a bug such as "Back after a form submit shows the wrong page".

```json
{ "history": "back" }
```

The target is not known before the move: it is the entry the browser has. So the result tells you where the tab arrived. This is a real response, Back after a sign-in form posted and the server redirected to `/today`:

```json
{
  "ok": true,
  "history": "back",
  "confirmed": true,
  "url": "http://127.0.0.1:58839/login",
  "sessionId": "s8ff1ba49-9376-436d-adf3-632193bfb07a"
}
```

`confirmed: true` means that the tab was seen to stop at `url`. Reticle waits until two looks in a row agree, so a route guard that replaces the route after Back is reported where it sent the tab, not where the tab passed through.

When there is no entry in that direction, the page refuses, and nothing waits:

```json
{
  "ok": false,
  "history": "forward",
  "reason": "the tab has no history entry in that direction on this origin"
}
```

The browser counts only the entries on the page's own origin. So Back from the first app page does not leave the app for the site the tab came from, or for the `about:blank` a leased tab opens on.

`confirmed: false` comes in three forms:

- With `waitedMs` and no `url`: the tab did not leave its page in the wait. Do not send the move again, because a second move goes one more entry. Call [`reticle_session`](/tools/sessions) to see where the tab is.
- With `url` and a note that the tab was still moving: `url` is where it was last seen, not proof that it stopped there.
- With `url` and a note that the page has no Reticle SDK: a leased tab went to a page Reticle cannot see into, and `url` is read from the browser.

A leased tab whose page has no SDK (an image, another site) moves through the browser, and its SDK reattaches when the tab is back on the app. A production drive refuses `history`, because the entry it lands on cannot be checked against the activated origin first.

## Arguments

| Argument | What it does |
| --- | --- |
| `url` | Where to go. Relative paths work |
| `reload` | Reload in place instead of navigating |
| `history` | `"back"` or `"forward"`: move one entry through the tab history, as the browser buttons do. Give it without `url` and `reload` |
| `hard` | With `reload`, bypass the cache. On a leased tab the browser reloads with its cache ignored (`hardReload: "cache_ignored"`). On a tab Reticle does not drive, only the document is fetched again, and scripts and modules can come from the cache (`hardReload: "document_only"`) |
| `timeout_ms` | How long to wait for the page to come back before `confirmed: false`. Default 5000; 0 looks once |

## Client-side routing is different

In a single-page app, clicking a link usually changes the route without destroying the document. That is a route change, not a navigation. Refs survive, and you can assert it directly:

```json
{ "ref": "e618", "action": "click", "until": { "kind": "route", "pathname": "/deployments" } }
```

That is a verified call. Its verdict quotes the transition itself:

```json
{
  "verified": "yes",
  "verdict": {
    "pass": true,
    "evidence": {
      "from": "http://localhost:4310/",
      "to": "http://localhost:4310/deployments",
      "pathname": "/deployments",
      "search": "",
      "hash": ""
    }
  }
}
```

Use `reticle_navigate` for a genuine document load. A deep link, a hard reload, or the first visit.
