**Four steps: run the installer once per machine, run `reticle init` once per project, then optionally `reticle connect` for the dashboard and `reticle push` to sync.** Skip `init` and your agent's first `reticle_session` call wires the app instead. Reticle embeds a dev-only SDK in your running app and proves a browser session connected. No account needed for steps 1 and 2.

By the end of this page your agent will click a button in your app and prove what happened: the request that fired, the state that changed, and the file to open if it didn't.

<Note>
  Every response on this page is real output, captured against a running app while writing it.
  Nothing here is illustrative.
</Note>

## Prerequisites

- Node 20.11 or newer
- A web app you can run locally, and its dev server
- A coding agent that speaks MCP (Claude Code, Cursor, Codex, OpenCode, Windsurf, VS Code)

## Step 1. Install it on this machine

In a terminal, before you open your coding agent:

<CodeGroup>

```bash macOS / Linux
curl -fsSL https://raw.githubusercontent.com/reticlehq/reticle/main/install/install.sh | sh
```

```powershell Windows
irm https://raw.githubusercontent.com/reticlehq/reticle/main/install/install.ps1 | iex
```

</CodeGroup>

This puts `reticle` on your PATH and registers the MCP server with every coding agent it can reach: Claude Code, Cursor, Windsurf, VS Code, Zed, Gemini CLI, Copilot CLI, OpenCode, Antigravity, Warp, Kiro, Amazon Q, Cline, Roo Code, Amp, Continue and Factory Droid. Nothing is asked. It does not wire your app, and says so: that is step 2. Want a verdict first? `reticle tutorial --run` drives Reticle's own demo app.

Codex CLI keeps a TOML config that Reticle will not rewrite itself, so with the `codex` command installed the installer registers Reticle through `codex mcp add`. Without it, the installer prints the lines to paste and the file to paste them into.

<Note>
  **Run this before opening your agent, and there is nothing to restart.** A coding agent reads its
  MCP server list once at startup. Install while it is closed and the tools are simply there when
  you open it. If it was already open, quit and reopen it once.
</Note>

Prefer not to pipe a script into a shell? The two commands it runs are:

```bash
npm install -g @reticlehq/server
npx @reticlehq/server setup mcp
```

## Step 2. Wire this project

In your project directory, before opening your coding agent:

```bash
RETICLE_INSTALL_SOURCE=docs_site npx @reticlehq/server init
```

This installs the dev-only SDK, wires your build config, starts the dev server, and checks that a browser session connected. Nothing from your project leaves your machine. If your dev server was already running, restart it once and hard-reload the tab: it read your build config before `init` edited it. Open your coding agent once this command finishes; if it was already open during installation, restart it to load the new tools. The `RETICLE_INSTALL_SOURCE` prefix is optional and only tells us which page you installed from. It is idempotent: run it twice and the second run reports what was already done rather than doing it again.

Step 1 is once per machine. This step is once per project. **Skipping it is the most common reason Reticle "does nothing":** the agent has the tools, but there is no app on the other end for them to see.

<Note>
  **Skipped this step?** Ask your agent to verify something in the app. Its first `reticle_session`
  call finds a project that has never connected, runs `init` there itself, and lists every file it
  changed under `wired`. Asked about something unrelated, it offers to wire the app instead of doing
  it. This works in Claude Code, Codex, Cursor and other MCP agents, including a second project
  while Reticle is already running for another one.
</Note>

Prefer to install the skill and let the agent run setup itself? On Claude Code the plugin registers the MCP server and the skill in one step:

```text
/plugin marketplace add reticlehq/reticle
/plugin install reticle@reticlehq
```

On Cursor, Codex, Copilot, Gemini and anything else the skills CLI supports:

```bash
npx skills add reticlehq/reticle
```

Then type `/reticle` and the agent runs the install from the skill.

Useful flags for the local-only `reticle init` path:

```
reticle init  [--dry-run] [--port N] [--no-mcp] [--no-install] [--app <dir>]
              [--env KEY=VALUE]... [--files-only] [--json] [--relaunch]
              --app picks WHICH app in a monorepo, when several are found
              --no-mcp skips MORE than the server registration: also the agent rule files
              (CLAUDE.md / AGENTS.md / .cursor) and the /reticle command, because all three
              only make sense once the tools are reachable.
```

Start with `reticle init --dry-run` if you want to see the app changes before anything is written.

<Tip>
  In a monorepo, `init` run at the root lists every app it found, each with its own
  `reticle init --app <dir>` line, and stops. Run the line for the app you want. With only one
  app, it wires that one without asking.
</Tip>

Prefer to wire it yourself? See [Manual install](/install-manual). It is about ten lines, and worth reading once even if you let the agent do it, because it explains what the agent actually changed.

## Step 3. Connect the dashboard (optional)

Skip this if you only want local verdicts. Everything above works without an account.

```bash
npx @reticlehq/server connect --project "My App"
```

`connect` runs Step 2 first if this project isn't wired yet, so you can use it in place of `init`. Then it:

1. Opens a browser so you can sign in, or create a free account at app.reticle.sh. Approve the short code shown in the browser and in the terminal, and the command carries on by itself.
2. Links this folder to the cloud project you named, creating it if it doesn't exist. `npx @reticlehq/server whoami` shows the link.
3. Sends the runs and flows already on this machine.

After that, every verified run syncs on its own. To sync right now, for example before showing a teammate:

```bash
npx @reticlehq/server push            # one sync
npx @reticlehq/server push --watch    # keep syncing while you work
```

The Free plan includes monthly Harness credits. What syncs, and how to switch each part off (`reticle config --runs/--memory/--flows on|off`), is in [What is recorded](/what-is-recorded). In CI, set `RETICLE_API_KEY` instead of signing in.

## Step 4. Check the setup

```bash
npx @reticlehq/server doctor
```

`doctor` diagnoses the whole setup in one command: Chromium, the daemon, the port. If something is wrong this is the page you want before you start debugging your app instead.

## Step 5. Open your app again when you need it

`init` (or `connect`) already started the dev server and opened the app. On a later day, start your dev server as usual, then:

```bash
npx @reticlehq/server open
```

This reuses the tab you already have open, or opens one if you don't. The SDK connects to the local daemon over a WebSocket, and your agent can now see the app.

<Warning>
  If the browser console says `[Reticle] this page could not open a websocket to …`, your app and
  the daemon disagree about the port. Set it explicitly: `RETICLE_PORT=4400 pnpm dev` (Vite
  plugin), `reticle({ port: 4400 })` in `vite.config`, or
  `reticle.connect({ url: 'ws://localhost:4400/reticle' })` by hand. This is
  the single most common setup problem, and the console message names the exact address it tried.
</Warning>

## Step 6. Look at the page

Ask your agent to take a snapshot. This is what came back from a real app:

```json
{
  "tree": "- textbox \"Email\" (ref=e3) [value=\"admin@reticle.dev\"]\n- textbox \"Password\" (ref=e4) [value=\"[REDACTED]\"]\n- button \"Sign in\" (ref=e5)",
  "nodes": 3,
  "truncated": false,
  "status": { "route": "/", "title": "Reticle · Mission Control" },
  "cost": { "bytes": 243, "tokens": 61 }
}
```

Three things to notice.

The password is already `[REDACTED]`. Reticle redacts credential-shaped values before they leave the page, so your agent's context never holds your test password, let alone your real one.

The whole snapshot cost **61 tokens**. This is `mode: "interactive"`, which returns only the controls. A full accessibility-tree dump of a comparable page runs to thousands. Reticle is built to ask narrow questions, because the answer gets re-sent to the model on every turn.

Each control has a `ref` like `e5`. That's the handle for the next step, and it stays valid until the element leaves the DOM, so you don't re-snapshot between actions.

## Step 7. Act, and prove it

Here is the whole idea of Reticle in one call. Your agent names the expected consequence **before** it acts:

```json
{
  "ref": "e5",
  "action": "click",
  "until": { "kind": "net", "method": "POST" }
}
```

Stating the expectation up front is the difference between a check and a rationalisation. An agent that clicks first and then decides what counts as success will always find something that counts.

The real response, trimmed for length:

```json
{
  "verified": "yes",
  "verifiedReason": "proved",
  "because": "assertion held at presence grade over a clean capture with no channel disagreeing",
  "effect": {
    "ok": true,
    "testid": "login-submit",
    "component": "Login",
    "name": "Sign in",
    "effect": { "domMutatedWithin": 7, "appeared": "Signing in…" },
    "source": { "file": "src/components/Login.tsx", "line": 81, "column": 8 }
  },
  "verdict": {
    "pass": true,
    "evidence": {
      "method": "POST",
      "url": "http://localhost:8787/api/login",
      "status": 200,
      "durationMs": 67,
      "requestBody": "{\"email\":\"admin@reticle.dev\",\"password\":\"[REDACTED]\"}",
      "responseBody": "{\"token\":\"[REDACTED]\",\"user\":{\"email\":\"admin@reticle.dev\"}}"
    }
  },
  "summary": {
    "net": { "total": 1, "errors": 0 },
    "consoleErrors": 0,
    "stateDiffs": [{ "path": "auth", "from": null, "to": "{\"email\":\"admin@reticle.dev\"}" }],
    "signals": ["auth:granted"]
  },
  "honesty": {
    "grade": "presence",
    "coverage": { "pct": 100, "partial": false },
    "integrity": { "clean": true, "issues": [] }
  }
}
```

![A real act_and_wait verdict, annotated. The verdict, the source pointer, the request evidence, the request count, the state diff, and the app's own signal](/images/verdict-annotated.png)

Read what that actually proves:

| Field | What it tells you |
| --- | --- |
| `verified: "yes"` | The named consequence happened. Not "the page looks different", the specific thing. |
| `source.file` / `line` | The button lives at `src/components/Login.tsx:81`. If this had failed, your agent knows which file to open. |
| `verdict.evidence` | The exact request: one `POST /api/login`, `200`, 67ms. Not a summary of it. The request. |
| `stateDiffs` | Application state moved from `null` to a real user. A mock that returns 200 without changing state is caught right here. |
| `signals` | The app's own `auth:granted` fired. This is the strongest signal available, because the app declared success itself. |
| `net.total: 1` | Exactly one request. Double-submit bugs show up as `2`. |
| `integrity.clean` | Nothing interfered with the capture, so the verdict is trustworthy. |

## What "verified" can say

<CardGroup cols={2}>
  <Card title="yes" icon="circle-check">
    The consequence you named actually happened, and the evidence is attached.
  </Card>
  <Card title="no" icon="circle-xmark">
    It did not happen. This is a finding, with the source pointer to go fix it.
  </Card>
  <Card title="unknown" icon="circle-question">
    Reticle drove the app and could not tell. **This is not a pass.** Report it as unknown.
  </Card>
  <Card title="no-fault" icon="circle-minus">
    Nothing was declared to prove, so nothing was checked. **Not a pass either:** add an `until`.
  </Card>
</CardGroup>

That third state is the one that matters. Most tools have two outcomes and quietly file "I couldn't tell" under "fine". A verification layer that cannot admit uncertainty is just a very confident random number generator.

## Frequently asked questions

<AccordionGroup>
  <Accordion title="How long does it actually take to install Reticle?">
    Two commands, and no restart if you run them in order. The installer registers the MCP server
    with every agent on the machine, so opening your agent afterwards is all that is needed. Then
    `npx @reticlehq/server init` wires the project, starts your dev server and opens the app for you. The MCP
    registration is global, so every later project starts with the tools already there.
  </Accordion>

<Accordion title="Do I need to write tests or learn a query syntax?">
  No. You talk to your agent in plain language and it calls the tools. There is no spec file, no
  selector language and no test runner involved in the loop on this page. If you later want the same
  flow to block a bad merge, you can save it and run it in CI, but that is a separate step.
</Accordion>

<Accordion title="Will any of this end up in my production build?">
  No. The SDK is dev-only. The Vite plugin declares `apply: 'serve'`, so it is dropped from `vite
  build` entirely, and `connect()` self-disables when the build reports `NODE_ENV=production`. The
  recommended wiring also guards the call behind `import.meta.env.DEV`, so there are two independent
  locks.
</Accordion>

<Accordion title="Does my code or my app's data leave my machine?">
  Not unless you link a project. The daemon runs on your machine and the SDK runs in your browser.
  Nothing from your app leaves the machine until you link a project (`reticle connect`, or
  `RETICLE_API_KEY` in CI). After that, what syncs is set by `reticle config`, and when the Harness
  drives, the platform sees the steps it drives. Secret values never leave. Anonymous product
  analytics are sent unless you opt out with `npx @reticlehq/server telemetry disable`, and they
  never include your code or your app's data.
</Accordion>

<Accordion title="What if my framework is not React or Next.js?">
  The core is framework-neutral, so DOM, network, console, routing and source mapping work anywhere
  JavaScript runs. What varies is how `connect()` gets into your app and whether you get component
  identity on top. See [Frameworks](/frameworks) for the exact wiring per stack and an honest table
  of what is gated in CI versus wired but unverified.
</Accordion>

  <Accordion title="Nothing connected. What is the first thing to check?">
    Run `npx @reticlehq/server doctor`. If it shows the daemon running but `sessions` at zero, your
    app is not reaching the bridge, and the usual cause is a port mismatch. The bridge port is not
    your dev-server port. See [Troubleshooting](/troubleshooting).
  </Accordion>
</AccordionGroup>
